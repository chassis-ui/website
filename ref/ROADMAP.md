# Chassis Website Roadmap

> **Status:** closed on 2026-10-05. This is the record of a project that ran from
> 2026-09-29 to 2026-10-05, and no longer a plan. What is left of it is tracked in the
> [issues](https://github.com/chassis-ui/website/issues), listed under
> [Open work](#open-work). New work starts as an issue, not here.
>
> **Scope:** what it took to make `chassis-website` and the `@chassis-ui/docs` package
> professional, production-ready and easy to contribute to. It changed this repository
> only. Work that belonged in a sibling repository was listed in `ref/SIBLING_TASKS.md`.
> That list was closed on 2026-10-05 with every task done or withdrawn, and then deleted. A sibling that
> names one of its tasks, such as A6 or CSS8, means a row of it:
> `git show 352e6e9:ref/SIBLING_TASKS.md`.
>
> **Baseline:** reviewed 2026-09-29 at `main` `24aa677`, `@chassis-ui/docs` 0.5.0. Every
> finding was checked against the code, the GitHub repository or the live site on that
> date.
>
> **Detail:** this file was condensed when it was closed. The task lists of each session
> and the session log are in its history. The last committed full version is at `352e6e9`:
> `git show 352e6e9:ref/ROADMAP.md`. It is from before the six issues were opened, so it

### Phase 0 — Green baseline

A red check means a real problem, and CI covers lint, types, the build and the audit.

- **Session 0.1, make CI pass.** Prettier over both packages, and the dependencies
  upgraded within their ranges, Astro to 7.3.5: the audit went from 34 advisories to none,
  with no overrides. The upgrade also moved the website from the 0.5.0-0 prereleases of
  `@chassis-ui/css` and `@chassis-ui/tokens` to 0.5.2 and 0.5.3, by decision.
- **Session 0.2, make CI mean something.** `check` and `check:astro` fail on an error. CI
  has a Build job: the production build, html-validate and the Nu Html Checker. The build
  uses the pinned commit of the submodule. Lighthouse runs on version 12, which reads
  `oklch()` colours. The workflows have read-only tokens and actions pinned by commit, and
  pull requests get a dependency review. The ruleset "Protect main and staging" is on
  (D1), with secret scanning, push protection and Dependabot alerts. Dependabot security
  updates stay off by decision. The files of F19 are deleted: the multi-platform content
  of `build/README.md` stays reachable at commit `24aa677` for `chassis-assets`.

### Phase 1 — Open issues and the consumer contract

Issues 1 and 2 had one cause: the package assumed that the site is built from the root of
the repository and that the source lives in that root.

- **Session 1.1, the fix.** Four optional keys in `config.yml`: `sourceDir`, `sourcePath`,
  `sitePath` and `siteBranch` (D2). The file components read the source through
  `libs/source.ts`, and "View on GitHub" links to the file of the page under `sitePath`.
- **Session 1.2, the release.** The consumer contract in the package README, a `LICENSE`
  and `engines` for the package, and 0.5.1, checked against scratch clones of chassis-css
  and chassis-tokens and released through `staging` and `main` (D16).

### Phase 2 — Package hardening

The package owns its contract, and a change that would break a consumer fails in this
repository before it is published. It produced 0.6.0, the breaking release, after the
prerelease 0.6.0-next.0 had proved the pipeline.

- **Session 2.1, own the contract.** `chassisDocs()` from `@chassis-ui/docs/integration`
  replaces the `@libs/*` aliases with virtual modules, which pages read through
  `@chassis-ui/docs/site` (D4, D17). The package has the config schema, strict and
  extendable, the path helpers, the remark plugins, `js/clipboard.ts`, `include` and
  `exclude` for `chassisAutoImport`, and `getPackageFilePath()`. The keys of `config.yml`,
  `sidebar.yml` and the frontmatter are camelCase (D18, D21). The versioning policy is in
  the package README (D19, D20) and the upgrade steps in `packages/docs/UPGRADING.md`.
  The website moved to the contract with a byte-identical build.
  [CONTRACT_REVIEW.md](CONTRACT_REVIEW.md) is the record of the seven copies it replaced.
- **Session 2.2, tests.** Vitest: unit tests of the libraries, component tests with the
  Astro container API in `packages/docs/test/fixture`, and tests of `api/contact.ts`. The
  job "Test" is a required check. The tests found F46 and F47.
- **Session 2.3, fixture sites.** The starter site, `packages/docs/starter`, is built in
  CI from the packed package in two layouts, `root` and `packages`: the job "Fixture
  Site", and `pnpm test:fixtures` locally. Reverting the fix for issue 2 fails both. The
  integration took over the workaround for two instances of `@chassis-ui/css` (F43). The
  fixture found F49 to F51.
- **Session 2.4, release pipeline.** Changesets, with the version made on `develop` and
  no release pull request (D5). The package has its own changelog, and the root one is
  the website's log by date (D11). `main` publishes with npm trusted publishing and
  provenance, prereleases under their own dist-tag, and only when Lint, Type Check, Test,
  Build and the fixture builds passed on the commit. This repository reads no npm token.
  `exports` lists the supported import paths by name. The integration puts the default
  `chassis-tokens` on the Sass load path (D22).

### Phase 3 — Contributor experience

A first-time contributor can clone, run, change and submit without asking.

- **Session 3.1, accurate docs and one way to run things.** Top-level scripts for what
  people type: `lint`, `format`, `test`, `check`, `preview`, and `build` as Vercel runs
  it. Setup and commands are in `CONTRIBUTING.md`, and `README.md` and `ref/DEVELOPMENT.md`
  link to it. Node 24 in `.nvmrc`, `engines` at
  `>=22.12.0` (D7). `ref/ARCHITECTURE.md` covers chassis-react and the `packages/site`
  layout. The docs section is a guide of three pages (D12). `examples/vanilla-html` stays,
  built with the site and linked from the examples page, and `react-app` is gone (D13).
  cspell runs in the Lint job. Search covers the blog posts and the guide. `pnpm dev` no
  longer moves the submodule pin: `pnpm vendor` builds the pinned commit and
  `pnpm sync-submodules` moves it. The branch flow is documented as it is used, with
  `develop` as the target of pull requests. The merged `dev/*` branches are deleted, and
  the maintainer deleted the four of F54 on 2026-10-05. Left: `app/docs`, issue 11.
- **Session 3.2, repository hygiene.** A code of conduct, a security policy with private
  vulnerability reporting, `CODEOWNERS`, a pull request template and issue forms, in
  `.github/` (D10). Labels for area and triage, Discussions, a pre-commit hook with
  lint-staged, and Dependabot weekly into `develop`. `ref/CHASSIS_CSS.md` matches the
  compiled CSS of 0.5.2 (F52). The tasks that were left became issues 6 to 11 on
  2026-10-05, without milestones.

### Phase 4 — Production hardening of the website

The site meets a stated bar for security, privacy, accessibility and performance, and CI
holds it there. Issues 6 to 10 are what is missing from that.

- **Session 4.1, security.** Five security headers in `vercel.json`, which the proxied
  sites get too. The content security policy is report-only and reports to
  `/api/csp-report`. The contact endpoint escapes its values, caps the body and the
  fields, checks the `Origin` header and is rate-limited by a rule of the Vercel firewall.
  `.env.example` names the three Resend variables, which Vercel needs for Preview as well
  as for Production. [VERCEL_CONFIG.md](VERCEL_CONFIG.md) explains each source of the
  policy and the firewall rule. Found and fixed: F55 and F56.
- **Session 4.2, routing.** `/react` is routed, for production and staging. The package
  has the `staticPath` option, since 0.6.2, for sites on other hosts. The Chassis sites do
  not use it: D6 was reversed on 2026-10-01, and every site loads the shared files from
  `/static/`. D6 was amended on 2026-10-04: each of the six project sites writes the files
  that Astro builds to `/<project>/static/astro/`. `build/check-links.js` checks links, anchors and assets, on
  the built site in the Build job and on each deployment in `links.yml`, where it crawls
  the proxied projects too. It found F57 to F60. F64 is a link that it passed and should
  not have, fixed in session 5.3.
- **Session 4.3, privacy and legal.** A consent banner in the package,
  `footer/Consent.astro`: Google Analytics loads only after the visitor accepts, and the
  choice is shared by the sites under chassis-ui.com (D14). A privacy page at `/privacy/`,
  linked from the footer of every site and from the contact form. The fonts stay on
  Google's servers (D15). F28 is settled: the code was written for Chassis.
- **Session 4.4, quality gates and operations.** `build/check-a11y.js` runs axe on every
  page of the built site, in both colour modes, in the Build job, without the contrast
  rule. It found F62. Lighthouse on staging tests the staging domain, each URL once (F40).
  [OPERATIONS.md](OPERATIONS.md) covers rollbacks, a proxied site that is down and the
  rotation of credentials. `build/check-csp.js` opens pages of a deployment in Chrome and
  lists what the policy would block, by hand and after each deployment in `csp.yml`: it
  replaces the stored reports (D23). Open from this session: issues 6 to 10.

### Phase 5 — Ecosystem support

This repository gives the siblings what they need to align. Whether and when a sibling
used it was that sibling's project.

- **Session 5.1, shared commands.** The package has a `chassis-docs` bin with `vendor`,
  `sync-submodules`, `html-validate` and `vnu` (D8). The website uses them and has no
  copy under `build/`.
- **Session 5.2, shared workflows and this repository's own upgrades.** Reusable
  workflows for lint, type check and build, which D24 withdrew on 2026-10-02: no sibling
  called them. One Node version for the ecosystem (D7). The website on
  `@chassis-ui/tokens` 0.6, with a byte-identical build. Every workflow has its actions
  pinned by commit, `persist-credentials: false` on each checkout and a timeout on each
  job. The assets submodule moved to `c42976e` on 2026-10-01 and to `def4a90` on
  2026-10-05 (F65), and the website keeps it (D9).
- **Session 5.3, canary and compatibility.** `build/canary.js` clones each sibling whose
  range accepts the version being released, installs the packed package and builds its
  site. `canary.yml` runs it on a version commit of `develop`, and it reports only. The
  package README has a compatibility table, with a row for each release.
- **Session 5.4, one workflow shape.** D24, on 2026-10-02. The publish workflow is
  `release.yml`, guarded against a manual run from another branch, and the trusted
  publisher on npmjs.com names it. Lint, Type Check and Build are jobs of `ci.yml` again,
  under those names, and the ruleset requires them with Test. Runs are cancelled for pull
  requests only. A Changeset job asks for a changeset when the published code of the
  package changes. The GitHub release is made with `gh release create`. The Audit job
  blocks on `pnpm audit --prod --audit-level moderate`.

## Breaking changes

Backward compatibility was not a goal of this project. The siblings were upgraded after
it, each in its own project.

- A sibling kept building on the version it had. Published versions do not change, and
  each sibling's lockfile pins one.
- The 0.5 line stayed non-breaking, because the siblings' ranges accepted it. 0.5.1 was
  its only release.
- The breaking changes shipped in 0.6.0. No sibling's range accepted it, so none took it
  by accident. Each has an entry in the package changelog and a step in `UPGRADING.md` of
  the package.

Since 0.6.0 the rule is "Versioning" in `packages/docs/README.md` (D19).

One thing is not covered by versions, and it still holds. `vercel.json` in this
repository acts on the live sibling sites at once. A rewrite that a deployed sibling uses
therefore stays until that sibling has been changed and deployed.

### Note on D10

GitHub reads default community files from one place only: a public repository named
`.github` in the organisation. This repository cannot take that role. That is the only
reason a new repository was proposed.

It is not needed. The recommendation is that each repository holds its own files:

- A default file is not part of the repository. It is missing from clones, from the file
  browser and from anything an agent or a contributor reads offline.
- A repository that has its own file ignores the default. tokens, css and react already
  have their own, so the default would serve four repositories, not seven.
- `CONTRIBUTING.md` differs per repository, because setup and commands differ. A shared
  default would be either vague or wrong.
- `CODE_OF_CONDUCT.md` and `SECURITY.md` are the same everywhere and change rarely. The
  cost of seven copies is low.
- A license cannot be inherited at all.

Shared workflows are different. A reusable workflow can live in any repository, so they
went here, in session 5.2. D24 withdrew them on 2026-10-02: no sibling called them, and
each repository has its own `ci.yml`, in one shape.
