## How to use this document

- The package has four releases that matter here. 0.5.1 is non-breaking and fixes the two
  open issues. 0.6.0 is breaking and replaces the alias contract. 0.6.1 and 0.6.2 are
  non-breaking: A5 and A15 need 0.6.1. All were published by
  2026-10-01. A sibling should go to 0.6.2 directly.
- The steps of the upgrade to 0.6 are in
  [UPGRADING.md](../packages/docs/UPGRADING.md) of the package. They were checked on
  scratch clones of `chassis-tokens` and `chassis-figma`. The tasks below name what is
  specific to a sibling.
- What was found in each sibling's copy of `src/libs` is in
  [CONTRACT_REVIEW.md](CONTRACT_REVIEW.md).
- A task with a value in "Needs" cannot start before this repository has shipped that
  release or finished that roadmap phase.
- A task with "nothing" in "Needs" can be done today.
- When a sibling finishes a task, set its status to done here. Session 5.3 of the roadmap
  removes finished tasks.
- Status values: `open`, `blocked`, `done`, `withdrawn`.

## What a sibling can rely on

- A sibling keeps building on the version in its lockfile. Nothing in this project
  changes a published version.
- Releases in the 0.5 line are non-breaking.
- From 0.6.0 on, what counts as a breaking change is written down: a change to what the
  package README documents. It is in the "Versioning" section of that README.
- 0.6.0 is a breaking release. tokens and assets are on `^0.6.2` and react on `^0.6.0`.
  css, icons and figma are on `^0.5.0-0`. Dependabot in css will propose 0.6; icons and
  figma have none. That pull request fails until the upgrade tasks are done, and it can
  wait.
- The referrer-based `/static/*` routing on the main site stays. Every site loads the
  shared static files from `/static/`, and the files that Astro builds from
  `/<project>/static/astro/`, which the main site routes by path (A6).
- Before a version of the package is published, the canary of this repository builds the
  site of every sibling whose range accepts it, from the sibling's default branch. A break
  shows on `develop` of this repository before the release. See "Releases" in its
  `CONTRIBUTING.md`.
- The shape of the workflows is decided, D24 of the roadmap: `ci.yml` on `develop` and
  pull requests, `release.yml` on `main`, the version made on `develop`. The website
  takes it in session 5.4; A26 to A33 say what each sibling changes.
- The checks of a commit run once, on `develop`. Pushing the same commit to `staging` or
  `main` runs nothing in Actions but the release on `main`.
- A sibling's `staging` branch and Vercel staging deployment stay. The staging host of
  the website routes to them. They are for previews, and no workflow of a sibling needs
  them.
