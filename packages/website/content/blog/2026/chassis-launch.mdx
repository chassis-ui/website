Chassis is now public. Before the feature list, I want to write about why it exists — because the project makes more sense if you understand what it's reacting against.

## The hard part isn't building the system

Every design system tutorial assumes the same starting point. One product, one brand, one platform, one team. Pick a primary colour, define some spacing scales, build a button. Done.

That's not the world I've been working in for the last decade. The projects I keep ending up on look more like this: three brands sharing roughly the same product but each with their own palette, typography and a marketing team that wants their version to be _just slightly different_. A web app, an iOS app, an Android app — different engineers, different frameworks, different opinions about how things should be built. A Figma file that has drifted from production by about six months and twelve un-merged variants. Three definitions of "primary blue" living in three places, all subtly different, all claiming to be the source of truth.

The pattern is the same every time: building the system isn't the hard part. Keeping it consistent — across brands, platforms, teams, and time — is. And almost every tool I tried was built to solve the small-system problem, not this one.

So a few years ago I started building the thing I wished existed. Chassis is what it became.

## Token-first, not component-first

The thing that finally clicked for me was changing what counts as the source of truth.

Most design systems start with components. You build a button, a card, an input. The tokens come later, generated from CSS variables, often retro-fitted to match what the components are already doing. That works fine for one brand. The moment you have two, the components stop being a source of truth and start being a translation layer — every brand needs its own forked version, every platform needs its own re-implementation.

Chassis flips that. Tokens are the source. Everything else — Figma variables, CSS classes, platform-specific outputs — consumes them. A change at the token layer propagates outward automatically. Swap the brand collection at the top; every output downstream updates. No forking, no manual handoff, no spreadsheet of "what changed this week".

It sounds obvious when you write it down. In practice almost no system is built this way, because doing it requires committing to it from the start.

## No translation layers

The other decision I'm proud of is naming.

In Chassis, the CSS class names match the Figma variable names. When a designer writes a spec that says `bg-surface-secondary`, that's a real Figma variable _and_ a real CSS class _and_ a real token. There's no "designer says one thing, code says another, somebody translates between them" layer.

That sounds small. It isn't. A startling amount of design system maintenance is just translation — one team's words into another team's words, then back again. Killing that loop changes how design and engineering work together.

## Five packages, one architecture

Chassis ships as five packages. [Tokens](/tokens) is the foundation. [CSS](/css) is the framework — Bootstrap-compatible, but every utility class is generated from tokens. [Figma](/figma) is the component library, bound to the same token definitions. [Icons](/icons) handles the SVG/sprite/font pipeline. [Assets](/assets) handles fonts and brand images.

You can adopt them independently, but they're designed to work as a single system. That's really the whole pitch — five separately-useful tools that share an architecture, so that adopting one of them makes the others easier to adopt later.

The full breakdown is on the [about page](/about) and in the docs. I'd rather not turn this post into a feature list.

## Who this is for

If you're building one product for one brand on one platform, Chassis is overkill. Pick something simpler.

But if any of this sounds familiar — multiple brands, multiple platforms, a Figma file drifted from production, three definitions of the same blue — then Chassis is built for you. Because it was built _from_ that situation, not for an idealised version of it.
